실습 7 · CONCEPT

GraphQL

클라이언트가 필요한 데이터의 형태를 직접 명시해서 요청하는 쿼리 언어. REST의 over/under-fetching을 해결합니다.

GraphQL은 HTTP 위에서 동작하므로 fetch로도 호출 가능합니다. 다만 별도 스키마/리졸버 설정이 필요해 이 실습 서버에는 포함하지 않았습니다. 아래 코드를 프로젝트에 추가하면 /graphql 및 /graphiql로 실습할 수 있습니다.

REST의 두 고질병

문제설명
Over-fetching이름만 필요한데 유저의 모든 필드를 받음
Under-fetching화면 하나 그리려 여러 엔드포인트를 N번 호출

① 스키마 (SDL)

type Query { user(id: ID!): User }
type User {
  id: ID!
  name: String!
  reservations: [Reservation!]!
}
type Reservation { id: ID!  checkIn: String!  hotel: Hotel! }
type Hotel { id: ID!  name: String! }

② 클라이언트 쿼리 → 필요한 것만

query {
  user(id: 1) {
    name
    reservations { checkIn  hotel { name } }
  }
}

③ 서버 (Spring for GraphQL)

@Controller
public class UserGraphQlController {
    @QueryMapping
    public User user(@Argument Long id) { return userService.findById(id); }

    @SchemaMapping(typeName = "User", field = "reservations")
    public List<Reservation> reservations(User user) {
        return reservationService.findByUserId(user.getId());
    }
}

fetch로 호출하는 형태

fetch('/graphql', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ query: '{ user(id:1){ name } }' })
});
대가: HTTP 캐싱 곤란(POST 단일 엔드포인트), N+1 문제(→ DataLoader 배치), 쿼리 복잡도 제어 필요. 다양한 클라이언트가 서로 다른 데이터 조합을 요구하는 BFF에 강점. 자세한 내용은 강의 문서 08장.

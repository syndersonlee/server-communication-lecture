CHAPTER 1

네트워크 기초

"HTTP는 TCP 위에서 돈다"는 말의 의미를, 계층 구조부터 차근차근 풀어봅니다.

계층 구조: OSI 7 & TCP/IP 4

통신은 너무 복잡해서 역할을 계층으로 분리합니다. 각 계층은 아래 계층의 기능만 사용합니다. 백엔드 개발자는 주로 Application과 Transport 계층을 다룹니다.

App
Application (7·6·5)
HTTP, WebSocket, gRPC, DNS — 우리가 코드로 다루는 영역
L4
Transport (4)
TCP, UDP, QUIC — 포트, 신뢰성, 흐름제어
L3
Internet (3)
IP, ICMP — IP 주소, 라우팅
L2
Network Access (2·1)
Ethernet, Wi-Fi, MAC
💡

데이터는 각 계층을 내려가며 헤더가 붙고(캡슐화), 받는 쪽에서 역순으로 벗겨집니다.

TCP vs UDP

전송 계층의 두 주인공. 거의 모든 상위 프로토콜이 이 둘 위에서 동작합니다.

🤝 TCP 연결형

  • 3-way handshake로 연결 수립
  • 신뢰성 보장: 순서·재전송·흐름/혼잡제어
  • 바이트 스트림 (메시지 경계 직접 관리)
  • HTTP, WebSocket, gRPC, DB 연결
VS

🚀 UDP 비연결형

  • 핸드셰이크 없음 → 지연 적음
  • 신뢰성 미보장: 그냥 던짐
  • 데이터그램 단위, 헤더 8byte로 가벼움
  • DNS, 영상 스트리밍, 게임, QUIC(HTTP/3)
⚠️

"TCP는 바이트 스트림" — send("AB"), send("CD")를 두 번 호출해도 받는 쪽은 "ABCD"로 한 번에 받을 수 있습니다. 그래서 Content-Length 같은 경계 표시가 필요합니다.

3-way Handshake

TCP는 연결을 맺기 위해 3번의 왕복을 합니다. 그래서 연결 수립은 비쌉니다.

Client
①→SYN
Server
←②SYN+ACK
Client
③→ACK
연결!
💡

매 요청마다 핸드셰이크를 하면 비싸므로, HTTP/1.1의 Keep-Alive, 커넥션 풀 같은 "연결 재사용" 기법이 등장합니다.

TCP는 어떻게 "신뢰성"을 만드는가

아래 계층의 IP는 패킷을 그냥 best-effort로 던질 뿐입니다 — 유실·중복·순서 뒤바뀜이 일어날 수 있죠. TCP는 그 위에서 "순서대로, 빠짐없이 도착하는 바이트 스트림"이라는 환상을 만들어 줍니다. HTTP·WebSocket·gRPC·DB 커넥션이 안심하고 데이터를 주고받는 건 전부 TCP 덕분입니다.

① 신뢰성의 3가지 장치

🔢 시퀀스 번호 + ACK

보내는 모든 바이트에 번호를 매기고, 받은 쪽은 "여기까지 받았다"는 ACK를 보냄. 송신자는 ACK로 도착을 확인.

🔁 재전송

ACK가 일정 시간 내 안 오거나(RTO 타임아웃) 중복 ACK가 3번 오면 → 해당 구간을 다시 전송.

📏 순서 재조립

늦게·뒤섞여 도착한 세그먼트를 번호 순으로 버퍼에 정렬한 뒤 애플리케이션에 올려줌.

Client
→SEQ=1 "ABCD"
Server
←ACK=5 (다음은 5번)
Client

유실되면? → ACK가 안 옴 → 송신자가 같은 구간을 재전송

② 흐름 제어 & 혼잡 제어

🪟 흐름 제어 (Flow Control)

수신자가 "내 버퍼에 이만큼 여유 있어"(receive window)를 알려주면, 송신자는 그만큼만 보냄.

  • 빠른 송신자가 느린 수신자를 압도하지 않게
  • 애플리케이션 백프레셔의 TCP 버전
+

🚦 혼잡 제어 (Congestion Control)

네트워크(중간 경로)가 막히면 전송 속도를 스스로 낮춤.

  • Slow Start로 천천히 늘렸다, 손실 감지 시 줄임
  • 모두가 회선을 공정하게 나눠 쓰도록
💡

흐름 제어 = 상대방 사정(수신 버퍼), 혼잡 제어 = 네트워크 사정(중간 경로 혼잡). 둘 다 "얼마나 빨리 보낼지"를 조절하지만 보는 대상이 다릅니다.

③ 연결 종료: 4-way Handshake & TIME_WAIT

연결을 맺을 땐 3번, 끊을 땐 4번 주고받습니다. 양쪽이 각자 독립적으로 "나는 더 보낼 거 없다(FIN)"를 선언하기 때문입니다.

Client
①→FIN
Server
←②ACK
Server
←③FIN
Client
④→ACK
종료

먼저 닫은 쪽은 잠시 TIME_WAIT 상태로 남음

⏳

TIME_WAIT은 버그가 아니라 정상입니다 — 뒤늦게 도착하는 패킷·재전송된 마지막 ACK가 다음 연결을 오염시키지 않도록 일정 시간 기다리는 것. 다만 매 요청마다 연결을 새로 맺고 끊으면 이게 수만 개씩 쌓여 포트가 고갈됩니다 → 커넥션 재사용으로 해결.

④ TCP의 함정: Head-of-Line Blocking

TCP는 "순서 보장"이 강점이자 약점입니다. 앞 세그먼트 하나가 유실되면, 뒤에 멀쩡히 도착한 데이터도 그게 재전송될 때까지 줄 서서 기다려야 합니다(HOL Blocking).

🧭

그래서 HTTP/2는 한 TCP 연결에 여러 스트림을 멀티플렉싱했지만 TCP 레벨 HOL은 여전했고, HTTP/3는 아예 전송을 UDP 기반 QUIC으로 바꿔 이 문제를 해결합니다. (2장에서 이어집니다)

⑤ 백엔드 개발자가 챙겨야 할 TCP 노브

⏱️ connect / read 타임아웃

connect=연결 수립 대기, read=응답 데이터 대기. 둘 다 명시하지 않으면 무한 대기로 스레드가 묶임.

♻️ 커넥션 풀 & Keep-Alive

3-way handshake 비용을 아끼려 연결을 재사용. HTTP 클라이언트/DB 풀의 핵심.

💓 TCP keepalive vs HTTP keep-alive

이름은 비슷하지만 다름 — TCP keepalive(SO_KEEPALIVE)는 죽은 연결 감지용, HTTP Keep-Alive는 연결 재사용용.

⚡ Nagle / TCP_NODELAY

작은 패킷을 모아 보내는 Nagle 알고리즘이 지연을 유발할 수 있음. 저지연 실시간 통신은 TCP_NODELAY로 끔.

⑥ 실전 예시: 은행 "전문(電文)" 통신

우리가 매일 쓰는 HTTP가 아니라, raw TCP 소켓 위에서 직접 메시지를 주고받는 대표적인 현업 사례가 바로 금융권의 전문(電文, message) 통신입니다. 은행 ↔ 금융결제원, 카드사 ↔ VAN, 펌뱅킹, ATM/CD기, 증권 시세/주문 등 상당수가 이 방식입니다.

전문이란 송수신 양측이 미리 약속한 규격의 메시지입니다. 보통 고정 길이(fixed-length)이거나 길이 헤더 + 바디 구조이고, 각 필드의 시작 위치와 길이가 명세로 고정되어 있습니다(카드 결제는 국제표준 ISO 8583이 대표적).

전형적인 전문 구조 (길이 헤더 + 바디)

LEN
길이부 (예: 4 byte)
바디 전체 길이 — TCP 바이트 스트림에서 "여기까지가 한 전문"을 알려주는 경계
HEAD
공통부 (헤더)
전문구분코드 · 송수신 기관코드 · 전문일시 · 일련번호(응답 매칭용) · 응답코드
BODY
개별부 (바디)
업무별 데이터 — 계좌번호(20) · 금액(13) · 거래구분(2) … 위치·길이 고정
전문 수신 — 길이부로 경계 잡기
DataInputStream in = new DataInputStream(socket.getInputStream());

while (true) {
    // ① 앞 4바이트 = 전문 길이 (ASCII 숫자, 예: "0058")
    byte[] lenBuf = in.readNBytes(4);
    int len = Integer.parseInt(new String(lenBuf, "EUC-KR"));

    // ② 길이만큼 "정확히" 읽어야 한 전문이 완성됨 (★ 핵심)
    byte[] body = in.readNBytes(len);

    // ③ 약속된 위치/길이로 필드 파싱
    Telegram msg = parseFixedLength(body);
    dispatch(msg.getSeqNo(), msg);   // 일련번호로 요청-응답 매칭
}
⚠️

왜 길이부가 필수인가 — 앞서 본 "TCP는 바이트 스트림" 때문입니다. 전문 2개를 연속으로 보내면 수신 측엔 "전문1전문2"가 한 덩어리로 도착하거나, 전문 하나가 여러 번에 쪼개져 올 수 있습니다. 그래서 길이부(또는 고정 길이)로 경계를 직접 잘라내야 합니다. read() 한 번 = 전문 한 개라고 가정하면 반드시 깨집니다.

🤔 왜 HTTP가 아니라 TCP 전문인가

초저지연·고TPS, 수십 년 된 금융 표준/레거시, 전용 금융망(VAN) 위 동작, HTTP 오버헤드 없이 상시 연결 유지가 필요하기 때문.

🔧 실무에서 챙기는 것

상시 연결 유지 + 주기적 heartbeat 전문, 끊기면 자동 재접속, 일련번호로 요청-응답 매칭, 인코딩(EUC-KR) 주의.

🧭

정리하면 — 전문 통신 = TCP 소켓(전송) + 고정 규격 메시지(경계·필드 약속). "신뢰성 있는 바이트 스트림" 위에 "업무 메시지 프레이밍"을 직접 얹은, TCP의 가장 날것(raw)에 가까운 활용입니다.

소켓과 BIO / NIO

소켓 = IP + Port. 모든 상위 프로토콜의 토대입니다. 서버가 연결을 처리하는 두 가지 방식이 이후 WebFlux 이야기로 이어집니다.

EchoServer.java
// 가장 원시적인 TCP 서버 (Spring 톰캣도 결국 이 위에서 동작)
try (ServerSocket server = new ServerSocket(8080)) {
    while (true) {
        Socket client = server.accept();  // 연결 올 때까지 블로킹
        // ... 읽고 응답 ...
    }
}

BIO (Blocking)

  • 연결 1개 = 스레드 1개
  • 동시 연결 1만 → 스레드 1만 → 메모리 폭발
  • 전통적 Spring MVC
VS

NIO (Non-blocking)

  • 적은 스레드로 많은 연결 (Selector/멀티플렉싱)
  • Netty · WebFlux의 기반
  • 6장에서 자세히

진단 도구 & 에러 대응

"연결이 안 돼요"의 90%는 아래 도구로 원인을 찾습니다.

🛟 에러별 대형 다이어그램으로 자세히 보기Connection refused·timeout·TIME_WAIT 포트 고갈을 "문제 → 대응" 흐름으로 크게 분석 트러블슈팅 →
ping / tracerouteCLI

대상까지 도달 가능한지·어디서 끊기는지 경로 추적.

nslookup / digCLI

DNS가 올바른 IP로 해석되는지 확인.

nc (netcat) / telnetCLI

nc -zv host 443 — 특정 포트가 열려 있는지(방화벽) 즉시 확인.

lsof / netstat / ssCLI

어떤 프로세스가 어떤 포트를 점유하는지, 연결 상태(TIME_WAIT 등) 확인.

tcpdump / WiresharkCLI

패킷 레벨로 핸드셰이크·재전송·RST를 직접 관찰.

openssl s_clientCLI

openssl s_client -connect host:443 — 인증서 체인·TLS 협상 점검.

Connection refused
원인

대상 포트에서 리스닝하는 프로세스가 없음(서버 미기동/포트 오타).

대응

ss -tlnp로 리스닝 확인, 서버 기동/포트 점검. 방화벽은 보통 "거부"가 아닌 "타임아웃"으로 나타남.

Connection timed out
원인

방화벽/보안그룹이 패킷을 드롭, 또는 경로상 네트워크 단절.

대응

보안그룹/방화벽 규칙 확인, nc -zv·traceroute로 어디서 막히는지 추적.

TIME_WAIT 소켓이 과다하게 쌓임
원인

매 요청마다 연결을 새로 맺고 끊음(커넥션 미재사용).

대응

Keep-Alive/커넥션 풀로 연결 재사용, 클라이언트 풀 크기 튜닝. (TIME_WAIT 자체는 정상 동작)

핵심 요약

  • 통신은 계층 구조로 분리 — 백엔드는 Application + Transport 집중
  • TCP(신뢰성·연결형) vs UDP(빠름·비연결형)
  • TCP 신뢰성 = 시퀀스/ACK · 재전송 · 순서 재조립 + 흐름/혼잡 제어
  • 연결: 수립 3-way, 종료 4-way → TIME_WAIT은 정상, 단 연결 재사용이 중요
  • TCP 순서 보장의 대가 = HOL Blocking → HTTP/3(QUIC)가 해결
  • 소켓 = IP+Port, BIO/NIO 차이가 대규모 동시성의 핵심

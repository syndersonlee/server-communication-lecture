CHAPTER 1

네트워크 기초

"HTTP는 TCP 위에서 돈다"는 말의 의미를, 계층 구조부터 차근차근 풀어봅니다.

계층 구조: OSI 7 & TCP/IP 4

통신은 너무 복잡해서 역할을 계층으로 분리합니다. 각 계층은 아래 계층의 기능만 사용합니다. 백엔드 개발자는 주로 Application과 Transport 계층을 다룹니다.

App
Application (7·6·5)
HTTP, WebSocket, gRPC, DNS — 우리가 코드로 다루는 영역
L4
Transport (4)
TCP, UDP, QUIC — 포트, 신뢰성, 흐름제어
L3
Internet (3)
IP, ICMP — IP 주소, 라우팅
L2
Network Access (2·1)
Ethernet, Wi-Fi, MAC
💡

데이터는 각 계층을 내려가며 헤더가 붙고(캡슐화), 받는 쪽에서 역순으로 벗겨집니다.

TCP vs UDP

전송 계층의 두 주인공. 거의 모든 상위 프로토콜이 이 둘 위에서 동작합니다.

🤝 TCP 연결형

  • 3-way handshake로 연결 수립
  • 신뢰성 보장: 순서·재전송·흐름/혼잡제어
  • 바이트 스트림 (메시지 경계 직접 관리)
  • HTTP, WebSocket, gRPC, DB 연결
VS

🚀 UDP 비연결형

  • 핸드셰이크 없음 → 지연 적음
  • 신뢰성 미보장: 그냥 던짐
  • 데이터그램 단위, 헤더 8byte로 가벼움
  • DNS, 영상 스트리밍, 게임, QUIC(HTTP/3)
⚠️

"TCP는 바이트 스트림" — send("AB"), send("CD")를 두 번 호출해도 받는 쪽은 "ABCD"로 한 번에 받을 수 있습니다. 그래서 Content-Length 같은 경계 표시가 필요합니다.

3-way Handshake

TCP는 연결을 맺기 위해 3번의 왕복을 합니다. 그래서 연결 수립은 비쌉니다.

Client
①→SYN
Server
←②SYN+ACK
Client
③→ACK
연결!
💡

매 요청마다 핸드셰이크를 하면 비싸므로, HTTP/1.1의 Keep-Alive, 커넥션 풀 같은 "연결 재사용" 기법이 등장합니다.

소켓과 BIO / NIO

소켓 = IP + Port. 모든 상위 프로토콜의 토대입니다. 서버가 연결을 처리하는 두 가지 방식이 이후 WebFlux 이야기로 이어집니다.

EchoServer.java
// 가장 원시적인 TCP 서버 (Spring 톰캣도 결국 이 위에서 동작)
try (ServerSocket server = new ServerSocket(8080)) {
    while (true) {
        Socket client = server.accept();  // 연결 올 때까지 블로킹
        // ... 읽고 응답 ...
    }
}

BIO (Blocking)

  • 연결 1개 = 스레드 1개
  • 동시 연결 1만 → 스레드 1만 → 메모리 폭발
  • 전통적 Spring MVC
VS

NIO (Non-blocking)

  • 적은 스레드로 많은 연결 (Selector/멀티플렉싱)
  • Netty · WebFlux의 기반
  • 6장에서 자세히

핵심 요약

  • 통신은 계층 구조로 분리 — 백엔드는 Application + Transport 집중
  • TCP(신뢰성·연결형) vs UDP(빠름·비연결형)
  • 연결 수립(3-way handshake)은 비싸다 → 연결 재사용이 중요
  • 소켓 = IP+Port, BIO/NIO 차이가 대규모 동시성의 핵심

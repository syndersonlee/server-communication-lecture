기술 선택 가이드

"정답인 기술은 없고, 상황에 맞는 기술이 있을 뿐." 모든 것을 한자리에 모읍니다.

전체 비교표

기술방향동기/비동기주 용도
HTTP/REST요청-응답동기범용 API, CRUD
gRPC단방향+스트리밍동기서버 간 고성능(MSA)
GraphQL요청-응답동기유연한 조회(BFF)
SSE서버→클라스트림알림·피드·시세·LLM
WebSocket양방향스트림채팅·게임·협업
Kafka/RabbitMQpub/sub·큐비동기이벤트, 디커플링

의사결정 트리

  1. 즉시 응답이 필요한가?

    아니오(던져놓고 잊음) → 비동기 메시징 (대용량·재처리 Kafka, 라우팅·작업큐 RabbitMQ, IoT MQTT)

  2. 실시간으로 계속 받아야 하나?

    아니오(단발성) → 서버 간 고성능 gRPC, 다양한 데이터 조합 GraphQL, 그 외 REST

  3. (실시간) 양방향이 필요한가?

    양방향 → WebSocket, 서버→클라면 충분 → SSE

  4. 서버 동시성 모델은?

    단순 → MVC, 고동시성+블로킹 라이브러리 → MVC+가상스레드, 스트리밍/백프레셔 → WebFlux/코루틴

실전 시나리오

🏨 숙소 예약 API

REST — 표준 CRUD·캐싱. 결제는 멱등키 적용

📊 예약 후속 처리

Kafka — 정산·알림·추천을 이벤트로 디커플링

🔔 실시간 예약 현황

SSE — 서버→클라 단방향, Redis Pub/Sub로 fan-out

💬 고객센터 채팅

WebSocket+STOMP — 외부 브로커로 스케일아웃

🔗 MSA 내부 통신

gRPC — 저지연 다수 호출. 외부는 REST

🤖 AI 컨시어지 스트리밍

SSE — LLM 토큰 스트리밍의 표준

성능·확장 공통 원칙

  1. 연결은 비싸다 → 재사용하라 (Keep-Alive, 커넥션 풀, HTTP/2)
  2. 단방향이면 양방향을 쓰지 마라 → SSE로 될 일에 WebSocket 금지
  3. 즉시 응답이 불필요하면 비동기로 → 응답 시간에서 무거운 작업 제거
  4. 재시도엔 멱등성을 → 중복 결제 방지
  5. 실시간 다중 서버는 fan-out 설계 → Redis Pub/Sub, 외부 브로커
  6. 장애를 전제로 설계 → 타임아웃, 서킷브레이커, DLQ, 백프레셔

🟠 Warning

gRPC DEADLINE_EXCEEDED

StatusRuntimeException: DEADLINE_EXCEEDED

호출이 설정한 deadline을 초과했습니다. 다운스트림 지연이 누적되며 연쇄적으로 번질 수 있습니다.

  • 체인 호출에서 DEADLINE_EXCEEDED
  • 일부 서비스 자원 점유 지속
⚠️원인
  • 다운스트림 지연
  • deadline 미설정/미전파
🩺진단
  • 분산 추적으로 느린 홉 식별
✅대응
  1. 호출마다 적절한 deadline 지정·전파
  2. 느린 RPC 분리/캐시
  3. 부분 결과는 스트리밍으로
🛡️
예방 — 모든 RPC에 기본 deadline, SLA 기반 예산(latency budget) 설계.

🔴 Critical

GraphQL 깊은 쿼리로 서버 과부하

악의적/실수로 깊게 중첩된 쿼리 → CPU·DB 폭주

클라이언트가 쿼리 형태를 정하는 GraphQL의 특성상, 제한이 없으면 한 요청이 서버를 마비시킬 수 있습니다.

🖥️서버제한 없음
💥
🔥과부하

💥 단 한 번의 쿼리가 자원을 소진

AFTER · 대응
🕳️깊은 쿼리
→
🚧depth/complexity 제한
✗거부
✅허용 쿼리만

✅ 깊이·복잡도 제한 + persisted query로 방어

🔍증상
  • 특정 쿼리에서 CPU/DB 폭주
  • 한 요청이 다수 자원 점유
⚠️원인
  • 깊은/넓은 중첩 쿼리
  • 제한·페이지네이션 부재
🩺진단
  • 느린 요청의 쿼리 depth/complexity 측정
✅대응
  1. max depth / complexity 제한 적용
  2. persisted query(허용 목록만)
  3. 페이지네이션·타임아웃 강제
🛡️
예방 — 공개 GraphQL은 복잡도 예산·요청 비용 분석을 기본 적용.
🔵 Info

GraphQL: HTTP 200인데 errors 배열에 에러

{ "data": {...}, "errors": [{ "message": "..." }] }

GraphQL은 부분 실패를 HTTP 상태코드가 아니라 응답 본문의 errors로 표현합니다. 상태코드만 보면 장애를 놓칩니다.

→
📱클라: 200이면 성공?

🐛에러 무시

→errors 검사

✅적절히 처리

✅ 항상 errors를 검사 + 일관된 에러 코드 체계

🔍증상
  • 모니터링은 200인데 사용자는 실패 경험
⚠️원인
  • 부분 실패를 errors로 표현
  • 클라가 상태코드만 신뢰
🩺진단
  • 응답 본문 errors 필드 점검
✅대응
  1. 클라가 errors를 반드시 확인
  2. 서버는 extensions.code로 표준 에러 코드
  3. 모니터링에 GraphQL errors율 포함
🛡️
예방 — 클라 공통 레이어에서 errors 처리 일원화.

TROUBLESHOOTING · HTTP

HTTP 에러 대응

실무에서 가장 자주 마주치는 HTTP/HTTPS 장애를, "문제 상황 → 대응 후" 흐름으로 크게 들여다봅니다.

읽는 법

각 에러마다 ① 큰 다이어그램(BEFORE 문제 / AFTER 대응) → ② 증상·원인·진단·대응 → ③ 예방 순서로 정리했습니다. 왼쪽 사이드바로 에러를 바로 이동할 수 있어요.

🔴 Critical

504 Gateway Timeout

HTTP/1.1 504 Gateway Timeout

게이트웨이/로드밸런서가 업스트림(앱) 응답을 제한 시간 안에 받지 못했습니다. 느린 쿼리·외부 호출·스레드 풀 고갈이 주범입니다.

무슨 일이 일어나는가

🧑‍💻Client
→
🚪LB / Gatewaytimeout 5s
⏳10s 대기
🖥️App
⏳느린 쿼리
🗄️DB8s 소요

💥 LB가 5초에 끊고 504 반환 → 앱은 계속 일하는데 응답은 버려짐

AFTER · 대응
🧑‍💻Client
→
🚪Gatewaytimeout 3s
→client<gateway
🖥️AppCB + 2s timeout
⚡빠른 실패
📊인덱스/캐시

✅ 타임아웃 계층 정렬 + 서킷브레이커로 빠른 실패, 느린 작업은 비동기 분리

🔍증상
  • 특정 API에서 간헐적/지속적 504
  • 응답 시간 p99가 게이트웨이 타임아웃 근처
  • 앱 로그엔 정상 처리인데 클라는 실패
⚠️원인
  • 느린 SQL·풀스캔, 외부 API 지연
  • 커넥션/스레드 풀 고갈로 대기
  • 타임아웃이 계층마다 제각각
🩺진단
  • APM/슬로우쿼리 로그로 느린 구간 특정
  • http.server.requests p99 확인
  • 풀 사용률(HikariCP active) 모니터
✅대응
  1. 느린 쿼리 → 인덱스/쿼리 개선, N+1 제거
  2. 타임아웃을 클라 < 게이트웨이 < 앱→DB 순으로 정렬
  3. 외부 호출에 서킷브레이커로 빠른 실패
  4. 무거운 작업은 비동기(큐)로 분리
🛡️
예방 — 모든 외부 호출에 타임아웃을 명시(기본값 무한 금지), p99 기반 알람, 부하 테스트로 풀 크기 사전 튜닝.
🔴 Critical

502 Bad Gateway

HTTP/1.1 502 Bad Gateway

게이트웨이가 업스트림으로부터 잘못된/끊긴 응답을 받았습니다. 주로 배포 중 인스턴스 교체나 OOM, 커넥션 강제 종료입니다.

무슨 일이 일어나는가
BEFORE · 문제
🧑‍💻Client
→
🚪LB
→연결 시도
💀App 인스턴스배포로 종료됨

💥 LB가 죽은 인스턴스로 트래픽을 보냄 → 연결 리셋/502

AFTER · 대응
🧑‍💻Client
→
🩺LB + 헬스체크
→정상만
🖥️정상 인스턴스
🔄교체 중(드레이닝)

✅ 헬스체크로 죽은 노드 제외 + 그레이스풀 셧다운으로 연결 드레이닝

🔍증상
  • 배포 직후 짧게 502 스파이크
  • 특정 인스턴스에서만 발생
⚠️원인
  • 롤링 배포 중 트래픽이 종료 노드로 감
  • OOM/패닉으로 프로세스 다운
  • keep-alive 타임아웃 불일치
🩺진단
  • LB 타깃 헬스 상태 확인
  • 앱 OOM/종료 로그, 메모리 추이
✅대응
  1. readiness/liveness 헬스체크 정확히 설정
  2. 그레이스풀 셧다운 + 커넥션 드레이닝
  3. 앱 keep-alive 타임아웃을 LB보다 길게
  4. OOM이면 힙/리소스 한계 점검
🛡️
예방 — 무중단 배포(블루-그린/카나리), readiness 통과 전 트래픽 차단, 메모리 알람.
🟠 Warning

CORS 차단

Access to fetch blocked by CORS policy: No 'Access-Control-Allow-Origin'

브라우저가 다른 출처(origin)로의 요청을 보안 정책으로 차단했습니다. 서버가 허용 헤더를 주지 않은 것이 핵심입니다.

프리플라이트(preflight) 흐름
BEFORE · 문제
🌐Browserapp.com
→OPTIONS
🖥️APIapi.com
✗ACAO 없음
🚫브라우저 차단

💥 서버 응답에 Access-Control-Allow-Origin이 없어 브라우저가 응답을 버림

AFTER · 대응
🌐Browser
→OPTIONS
🖥️APIACAO: app.com
✓허용
✅실제 요청 진행

✅ 서버가 허용 출처·메서드·헤더를 응답 → 본 요청 진행

🔍증상
  • 브라우저 콘솔에 CORS 에러
  • 서버 로그엔 200인데 화면은 실패
  • OPTIONS 요청이 4xx
⚠️원인
  • 서버가 CORS 헤더 미응답
  • 커스텀 헤더/메서드 미허용
  • credentials 사용 시 와일드카드 불가
🩺진단
  • DevTools에서 OPTIONS 응답 헤더 확인
  • curl -i -X OPTIONS로 직접 점검
✅대응
  1. 서버에 글로벌 CorsConfiguration 설정
  2. 허용 origin/method/header 명시
  3. 쿠키 인증이면 allowCredentials=true + 정확한 origin
  4. 운영은 * 대신 도메인 화이트리스트
🛡️
예방 — 게이트웨이 한 곳에서 CORS 정책 일괄 관리, 환경별 허용 도메인 분리.
🟠 Warning

TLS 인증서 검증 실패 (PKIX)

javax.net.ssl.SSLHandshakeException: PKIX path building failed

클라이언트(JVM)의 신뢰 저장소(truststore)에 상대 서버의 CA 인증서가 없어 TLS 핸드셰이크가 실패했습니다.

신뢰 체인 검증

🔐TLS
🖥️Server사내 CA 서명
✗CA 없음
⛔검증 실패

💥 신뢰 체인을 만들 CA가 truststore에 없음 → 핸드셰이크 중단

AFTER · 대응
☕JVM Client+ 사내 Root CA
🔐TLS
🖥️Server
✓체인 OK
🔒암호화 통신

✅ CA를 truststore에 등록하면 신뢰 체인 완성

🔍증상
  • 외부/사내 HTTPS 호출 시 SSLHandshakeException
  • brew/로컬은 되는데 서버에선 실패
⚠️원인
  • 자체 서명/사설 CA 미등록
  • 중간 인증서 체인 누락
  • 도메인-인증서 CN/SAN 불일치
🩺진단
  • openssl s_client -connect host:443로 체인 확인
  • -showcerts로 중간 CA 누락 점검
✅대응
  1. CA를 JVM truststore에 추가 (keytool -importcert)
  2. 서버는 인증서 풀체인을 제공하도록 설정
  3. 도메인-SAN 일치 확인
🛡️
예방 — 사내 CA 배포 자동화, 인증서 만료 모니터링, 컨테이너 이미지에 CA 번들 포함.
🟠 Warning

429 Too Many Requests

HTTP/1.1 429 Too Many Requests · Retry-After: 2

레이트 리밋(서버 또는 호출 대상 API의 쿼터)을 초과했습니다. 무지성 재시도는 상황을 더 악화시킵니다.

재시도 전략의 차이
BEFORE · 문제
🔁즉시 재시도x100
⇉폭주
🖥️APIrate limit
✗
🌊429 더 심해짐

💥 즉시·동시 재시도가 thundering herd를 만들어 한도를 계속 때림

AFTER · 대응
⏱️백오프+지터1·2·4s±
→완만히
🪣토큰 버킷
→
✅API 200

✅ Retry-After 존중 + 지수 백오프·지터 + 자체 스로틀링

🔍증상
  • 외부 API 호출이 429로 실패
  • 피크 시간대 집중 발생
⚠️원인
  • 쿼터/RPS 한도 초과
  • 재시도 증폭(retry storm)
🩺진단
  • 응답 헤더의 Retry-After·rate limit 헤더 확인
  • 호출량 대시보드 점검
✅대응
  1. Retry-After를 반드시 존중
  2. 지수 백오프 + 지터로 재시도 분산
  3. 호출 측 토큰버킷으로 자체 스로틀
  4. 가능하면 배치/캐시로 호출량 자체 감소
🛡️
예방 — 클라이언트 레이트리미터 내장, 캐싱으로 중복 호출 제거, 쿼터 상향 협의.
🔴 Critical

재시도로 인한 중복 처리 (이중 결제)

POST 재시도 → 같은 주문이 2번 결제됨

멱등하지 않은 POST가 네트워크 오류 후 재시도되어 동일 작업이 중복 수행됐습니다. 돈이 걸린 가장 위험한 케이스입니다.

멱등키(Idempotency-Key)의 역할
BEFORE · 문제
🧑‍💻Client
→POST(타임아웃)
💳결제 #1
🔁재시도
💳결제 #2중복!

💥 첫 응답이 유실됐을 뿐 결제는 성공 → 재시도가 두 번째 결제 생성

AFTER · 대응
🧑‍💻ClientKey: abc-123
→POST + Key
🗝️서버: Key 확인
🔁같은 Key
✅기존 결과 반환결제 1회

✅ 같은 멱등키 요청은 한 번만 처리하고 저장된 결과를 반환

🔍증상
  • 동일 주문에 결제/적립 2건
  • 네트워크 불안정 구간에서 증가
⚠️원인
  • 비멱등 POST의 재시도
  • 타임아웃 후 성공 여부 모름
🩺진단
  • 중복 트랜잭션 로그/타임스탬프 비교
  • 클라 재시도 로직 점검
✅대응
  1. 요청에 Idempotency-Key 헤더 부여
  2. 서버가 키별 처리 결과를 저장(예: Redis)
  3. 같은 키 재요청은 저장 결과를 그대로 반환
  4. DB 유니크 제약으로 이중 안전망
🛡️
예방 — 결제·주문 등 금전 API는 기본으로 멱등키 적용, 클라 SDK에서 자동 부여.

WebFlux & 코루틴

시선을 서버 안쪽으로 — "이 통신들을 처리하는 서버의 동시성 모델을 어떻게 가져갈 것인가?"

⏱ 약 30분🎯 사용 케이스 · 도구 · 에러 대응

출발점: Thread-per-Request의 한계

전통적 Spring MVC(톰캣)는 요청 1개 = 스레드 1개입니다. 문제는 I/O 대기 — DB나 외부 API 응답을 기다리는 동안 그 스레드는 아무 일도 안 하면서 점유됩니다.

A
요청 A · 스레드1
DB 호출(50ms) ⏳ 외부API(200ms) ⏳ ← 그동안 스레드는 "놀고 있음"
B
요청 B · 스레드2
⏳ 대기 중...
…
요청 N · 스레드 풀 고갈
큐에서 대기 → 지연 폭발 💥
💡

대부분의 백엔드는 CPU가 아니라 I/O 대기가 병목입니다. "노는 스레드"를 줄이면 같은 자원으로 훨씬 많은 동시 요청을 처리할 수 있습니다. 스레드는 비쌉니다(스택 ~1MB).

WebFlux (리액티브)

Netty 기반 논블로킹 I/O + 이벤트 루프. 적은 수의 스레드(보통 CPU 코어 수)가 수많은 요청을 번갈아 처리합니다. I/O는 콜백으로 넘기므로 스레드가 노는 일이 없습니다.

이벤트 루프
스레드 4개
⇉논블로킹
동시 요청
수만 개

Mono와 Flux

Mono<T>

0~1개 결과를 비동기로 발행 (단건)

Flux<T>

0~N개 결과를 비동기로 발행 (스트림)

WebFlux Controller
@GetMapping("/{id}")
public Mono<UserProfile> getProfile(@PathVariable Long id) {
    Mono<User>  user  = repository.findById(id);          // 논블로킹 DB(R2DBC)
    Mono<Grade> grade = webClient.get().uri("/grades/"+id)
                          .retrieve().bodyToMono(Grade.class); // 논블로킹 호출

    return Mono.zip(user, grade)              // 어느 스레드도 블로킹 안 함
               .map(t -> new UserProfile(t.getT1(), t.getT2()));
}

백프레셔 (Backpressure) — 리액티브의 진짜 무기

생산자가 소비자보다 빠르면 데이터가 쌓여 OOM이 납니다. 리액티브 스트림은 소비자가 "N개만 더 줘"라고 요청하는 흐름 제어를 표준으로 지원합니다.

Publisher
→request(10)
Subscriber

감당할 만큼만 → 대용량 스트리밍을 안전하게

⚠️

WebFlux의 함정: 파이프라인 어딘가에서 블로킹 코드(JDBC·동기 라이브러리)를 호출하면 이벤트 루프가 막혀 전체 성능이 붕괴합니다. 위에서 아래까지 전부 논블로킹(R2DBC, WebClient)이어야 합니다.

Kotlin 코루틴

Mono/Flux 체이닝은 강력하지만 읽기 어렵고 디버깅이 힘듭니다. 코루틴은 논블로킹인데 동기 코드처럼 보이게 씁니다.

UserController.kt
// suspend: 논블로킹이지만 위에서 아래로 읽히는 평범한 코드처럼
@GetMapping("/{id}")
suspend fun getProfile(@PathVariable id: Long): UserProfile = coroutineScope {
    val user  = async { repository.findById(id) }   // 동시에 시작
    val grade = async { gradeClient.fetch(id) }     // 동시에 시작
    UserProfile(user.await(), grade.await())       // 둘 다 끝나면 조합
}

⏸ suspend

중단되면 스레드 반납, 결과 오면 이어서 → 논블로킹

🌳 구조적 동시성

스코프 자식 작업이 생명주기 공유 → 누수/취소 누락 방지

🌊 Flow

코루틴 버전의 Flux (백프레셔 지원)

💡

같은 논블로킹이라도 Reactor는 함수형 선언적, 코루틴은 명령형(절차적). 코루틴은 콜백 지옥 없이 비동기를 직관적으로 표현합니다.

게임 체인저: 가상 스레드 (Java 21+)

Project Loom의 가상 스레드는 "블로킹 코드 스타일 그대로 + 높은 동시성"을 가능하게 합니다. 2026년 현재 빼놓을 수 없는 주제입니다.

🪶 초경량

JVM이 관리, 수십만~수백만 개 생성 가능

🔄 자동 양보

블로킹(JDBC) 시 OS 스레드를 점유하지 않고 unmount

application.yml
# Spring Boot 3.2+ : 한 줄로 가상 스레드 활성화
spring:
  threads:
    virtual:
      enabled: true
🔥

판도 변화: "높은 동시성 = 무조건 WebFlux"라는 공식이 약해졌습니다. 단순 I/O 동시성만 필요하면 복잡한 리액티브 대신 MVC + 가상 스레드가 더 쉬운 선택일 때가 많습니다. 단, 백프레셔가 필요한 스트리밍은 여전히 리액티브의 영역입니다.

언제 무엇을 쓰나

✅ WebFlux/코루틴이 좋을 때

  • 동시 연결이 매우 많고 요청마다 다수의 느린 I/O(MSA 팬아웃)
  • 스트리밍 + 백프레셔 (대용량 데이터, 대규모 SSE)
  • 게이트웨이/프록시 등 I/O 중계가 주 업무
  • 코루틴: Kotlin 팀 + 가독성 유지
VS

🚫 피하는 게 나을 때

  • 일반 CRUD / 내부 어드민
  • 블로킹 라이브러리(JDBC/JPA)가 많음
  • CPU 바운드가 주력
  • 팀 리액티브 숙련도 낮음 → 디버깅 리스크

의사결정 트리

  1. 높은 I/O 동시성이 필요한가?

    아니오 → Spring MVC (단순·검증됨)

  2. 백프레셔/스트리밍이 필요한가?

    예 → WebFlux(Java) 또는 코루틴 Flow(Kotlin)

  3. 블로킹 코드를 끝까지 논블로킹으로 바꿀 수 있나?

    어렵다/팀 미숙 → MVC + 가상 스레드 (쉬운 고동시성)
    가능/이미 리액티브 → WebFlux 또는 코루틴

세팅 & 도구

spring-boot-starter-webfluxLIB

Reactor Netty 기반 논블로킹 스택. MVC와 동시 사용은 지양(둘 중 하나).

R2DBCLIB

논블로킹 DB 드라이버. JDBC를 쓰면 WebFlux 이점이 사라진다.

BlockHoundLIB

이벤트 루프에서 블로킹 호출을 런타임에 탐지. WebFlux의 필수 안전장치.

Reactor 디버깅LIB

Hooks.onOperatorDebug() / checkpoint()로 의미 있는 스택 트레이스 확보.

kotlinx-coroutines + FlowLIB

Kotlin에서 suspend 컨트롤러·Flow 스트리밍.

가상 스레드 (Java 21+)JVM

spring.threads.virtual.enabled=true로 MVC에서 손쉬운 고동시성.

에러 케이스 & 대응

🛟 에러별 대형 다이어그램으로 자세히 보기블로킹 호출·subscribe 누락·스택트레이스·백프레셔·컨텍스트 유실을 크게 분석 트러블슈팅 →
갑자기 전체 응답이 느려지고 처리량 급락
원인

이벤트 루프 스레드에서 블로킹 호출(JDBC, 동기 SDK, Thread.sleep) 발생 → 소수의 루프 스레드가 막힘.

대응

블로킹 작업은 Schedulers.boundedElastic()로 격리, R2DBC/논블로킹 클라이언트로 교체, BlockHound로 탐지.

의미를 알 수 없는 Reactor 스택 트레이스
원인

비동기 연산자 체인은 호출 스택이 끊겨 어디서 났는지 보기 어려움.

대응

checkpoint("설명") 삽입, 개발 환경에서 Hooks.onOperatorDebug(), reactor-tools 적용.

아무 일도 안 일어남 (요청해도 응답 없음)
원인

리액티브 시퀀스를 구독(subscribe)하지 않음. "구독해야 흐른다"는 lazy 특성.

대응

컨트롤러는 Mono/Flux를 반환(프레임워크가 구독). 임의로 .subscribe()를 흘려 만들지 말 것.

OutOfMemory / 데이터 폭주
원인

빠른 생산자 + 느린 소비자인데 백프레셔 미적용.

대응

onBackpressureBuffer/Drop, limitRate()로 흐름 제어. 무한 스트림에 적절한 경계.

컨텍스트(MDC/트랜잭션/시큐리티)가 사라짐
원인

스레드가 계속 바뀌어 ThreadLocal 기반 컨텍스트가 전파 안 됨.

대응

Reactor Context 사용, @Transactional은 리액티브 트랜잭션 매니저, 시큐리티는 ReactiveSecurityContext.

핵심 요약

  • 병목은 보통 I/O 대기. Thread-per-request는 "노는 스레드"로 자원 낭비
  • WebFlux: 이벤트 루프 + Mono/Flux + 백프레셔. 강력하지만 끝까지 논블로킹이어야 하고 어렵다
  • 코루틴: 논블로킹인데 동기처럼 읽힘. Reactor보다 직관적(Kotlin)
  • 가상 스레드: 블로킹 코드 그대로 고동시성 → "고동시성=WebFlux" 공식을 흔듦

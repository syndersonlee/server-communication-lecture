Protocol Buffers (Protobuf) 심화

"데이터를 어떻게 작고 빠르게 주고받을 것인가" — 구글이 만든 언어 중립 바이너리 직렬화 포맷. gRPC의 기본 포맷이자, 게임 산업의 사실상 표준 패킷 포맷입니다.

⏱ 약 25분🎯 와이어 포맷 · 스키마 진화 · 게임 활용

Protobuf란 무엇인가

Protobuf는 스키마(.proto)를 먼저 정의하고, 그 스키마로 여러 언어의 코드를 자동 생성하며, 데이터를 조밀한 바이너리로 직렬화합니다. JSON·XML과 같은 "데이터 표현 포맷"이지만 사람이 읽는 텍스트가 아니라 기계를 위한 압축적 바이너리라는 점이 핵심입니다.

📜 스키마 우선

.proto가 단일 진실 공급원(SSOT). 계약을 코드로 강제.

🌐 언어 중립

하나의 스키마 → Java·C#·C++·Go·Python… 코드 생성.

📦 조밀한 바이너리

필드명을 보내지 않고 번호+타입만 → JSON 대비 30~60% 작음.

💡

JSON은 {"playerId": 12345}처럼 키 이름까지 매번 전송합니다. Protobuf는 스키마에서 "1번 필드 = playerId"를 미리 약속했으므로, 네트워크엔 "1번 필드에 12345"만 흐릅니다. 키 이름이 사라지는 만큼 작고 빠릅니다.

왜 작고 빠른가 — 와이어 포맷

Protobuf의 각 필드는 (필드번호 · 와이어타입) 태그 1바이트 + 값으로 인코딩됩니다. 정수는 varint(작은 수일수록 적은 바이트)로 저장돼, 대부분의 게임 패킷처럼 작은 값이 많은 데이터에서 극적으로 작아집니다.

같은 데이터, 다른 크기

JSON
{"id":12345,"x":3,"y":7,"hp":100}
약 34 bytes — 키 이름·따옴표·콤마 모두 전송
PB
08 b9 60 10 03 18 07 20 64
약 9 bytes — 번호+값만. varint로 작은 수는 1바이트

varint

작은 정수는 1바이트, 큰 정수만 늘어남. 좌표·HP·카운트 등에 유리.

태그 = 번호 << 3 | 타입

필드를 번호로 식별 → 필드명 문자열 불필요, 순서 무관.

⚠️

바이너리라서 사람이 바로 못 읽고 디버깅이 번거롭습니다(스키마 없이는 해석 불가). 또한 Protobuf는 압축도 암호화도 아닙니다 — 민감 데이터는 TLS, 큰 페이로드는 별도 압축(gzip/zstd)을 함께 써야 합니다.

스키마 작성 (proto3)

메시지(message)·열거형(enum)·반복(repeated)·맵(map)·oneof 등으로 데이터를 표현합니다. 게임에서 자주 쓰는 형태를 모았습니다.

game.proto
syntax = "proto3";
package game;

// 좌표 — 작은 정수가 많아 varint 효율이 큼
message Vec3 {
  float x = 1;
  float y = 2;
  float z = 3;
}

enum Team {
  TEAM_UNKNOWN = 0;   // proto3는 0번 기본값 필수
  TEAM_RED     = 1;
  TEAM_BLUE    = 2;
}

// 플레이어 상태 스냅샷(서버→클라 브로드캐스트)
message PlayerState {
  uint32 player_id = 1;
  Vec3   position  = 2;
  float  yaw       = 3;
  uint32 hp        = 4;
  Team   team      = 5;
  repeated uint32 buff_ids = 6;  // 가변 길이 목록
}
🔑

필드 번호는 영원한 식별자입니다. 1~15번은 태그가 1바이트라 자주 쓰는 필드에 우선 배정하면 패킷이 더 작아집니다(게임 좌표·HP 등).

핵심 패턴: oneof 메시지 봉투(Envelope)

실시간 게임에서는 한 연결로 수십 종류의 메시지(입력·이동·채팅·스킬…)가 흐릅니다. 이를 하나의 봉투(Envelope) 메시지 + oneof로 감싸면, 단일 채널에서 타입 안전하게 라우팅할 수 있습니다. 게임 서버의 거의 표준 패턴입니다.

envelope.proto
// 클라→서버 입력
message InputCommand {
  uint32 seq        = 1;   // 클라 시퀀스(재전송/보정용)
  bool   move_fwd   = 2;
  bool   fire       = 3;
  float  aim_yaw    = 4;
}
message ChatMessage { uint32 from = 1; string text = 2; }
message Ping        { uint64 client_time_ms = 1; }

// 한 채널로 흐르는 모든 메시지를 감싸는 봉투
message ClientEnvelope {
  oneof payload {
    InputCommand input = 1;
    ChatMessage  chat  = 2;
    Ping         ping  = 3;
  }
}

🎮 게임 산업에서의 활용

게임은 "초당 수십 번, 수많은 플레이어에게" 상태를 주고받습니다. 대역폭·지연·CPU가 곧 체감 품질이라, 작고 빠른 Protobuf가 자연스럽게 표준이 되었습니다.

🕹️

실시간 멀티플레이 패킷

이동·입력·스킬을 tick(예: 20~60Hz)마다 직렬화. 작은 페이로드 + 빠른 파싱으로 대역폭·지연 최소화.

WebSocket/UDP + PB
🤝

클라↔서버 공용 스키마

Unity(C#)·Unreal(C++) 클라이언트와 Java/C++/Go 서버가 하나의 .proto를 공유 → 직렬화 버그·타입 불일치 차단.

Polyglot
🧩

백엔드 마이크로서비스 간은 gRPC + Protobuf로 저지연 호출(매칭, 상점, 진행도 저장).

gRPC
💾

스키마 진화가 쉬워 저장 포맷으로도 적합. 입력 로그를 PB로 쌓아 리플레이/치팅 분석.

🧭

분리가 핵심 — Protobuf는 "무엇을 보낼지(데이터 형태)"를 담당하고, "어떻게 보낼지(신뢰성·순서·재전송)"는 전송 계층(TCP/UDP)이 담당합니다. 같은 PB 메시지를 TCP로도 UDP로도 흘릴 수 있습니다.

예시 ① 클라이언트(Unity · C#)에서 입력 전송

NetworkClient.cs
// protoc로 생성된 C# 타입 사용
var env = new ClientEnvelope {
    Input = new InputCommand {
        Seq = ++_seq, MoveFwd = true, Fire = false, AimYaw = aim
    }
};
byte[] bytes = env.ToByteArray();   // 직렬화 (수 바이트)
_socket.Send(bytes);                  // WebSocket/UDP로 전송

예시 ② 서버(Java)에서 봉투 해석·라우팅

GamePacketHandler.java
ClientEnvelope env = ClientEnvelope.parseFrom(bytes); // 역직렬화

switch (env.getPayloadCase()) {           // oneof 분기
    case INPUT -> applyInput(playerId, env.getInput());
    case CHAT  -> broadcastChat(env.getChat());
    case PING  -> sendPong(playerId, env.getPing());
    case PAYLOAD_NOT_SET -> log.warn("empty packet");
}

예시 ③ 서버→클라 상태 브로드캐스트(스냅샷)

snapshot.proto
// 한 tick의 모든 가시 플레이어 상태를 묶어 전송
message WorldSnapshot {
  uint32 tick = 1;
  repeated PlayerState players = 2;  // 관심 영역(AOI)만 포함
}
⚡

실무 최적화: 델타 압축(직전 스냅샷 대비 변경 필드만), 관심 영역(AOI)으로 가까운 플레이어만 포함, 좌표를 float 대신 sint32(고정 스케일)로 양자화 — 모두 PB 위에서 자연스럽게 적용됩니다.

스키마 진화 & 라이브 운영

라이브 게임은 클라이언트 구버전과 서버 신버전이 공존합니다. Protobuf는 호환 규칙만 지키면 무중단으로 필드를 추가할 수 있습니다.

✅ 안전한 변경

  • 새 필드를 새 번호로 추가 (구버전은 무시)
  • 필드 삭제 시 번호를 reserved로 영구 봉인
  • enum에 값 추가(0번은 UNKNOWN 유지)
VS

🚫 깨지는 변경

  • 필드 번호 재사용/변경 → 데이터 오염
  • 타입 변경(호환 안 되는 와이어타입)
  • required 의존(proto3엔 없음)·의미 변경
진화 예시
message PlayerState {
  uint32 player_id = 1;
  Vec3   position  = 2;
  // ... 기존 필드 ...
  reserved 7;              // 과거 'stamina' 삭제 → 번호 재사용 금지
  uint32 skin_id = 8;     // 신규: 구버전 클라는 그냥 무시
}
🛡️

buf로 CI에서 breaking change 검사를 자동화하면, 라이브 클라이언트를 깨는 스키마 변경을 머지 전에 막을 수 있습니다.

도구 & 대안

protocCLI

공식 컴파일러. --csharp_out·--java_out·--cpp_out으로 클라/서버 코드 생성.

bufCLI

린트·포맷·호환성(breaking) 검사·원격 생성. 모던 protobuf 워크플로의 표준.

protobuf-net / Google.ProtobufC#

Unity 클라이언트용 런타임. IL2CPP/AOT 환경 호환 확인 필요.

protoc-gen-validateLIB

🧭

대부분의 게임은 Protobuf로 충분합니다. 매 프레임 대량 객체를 읽기만 하는 극단적 경로(예: 거대한 월드 스냅샷, 에셋)에서 파싱 비용이 문제될 때 FlatBuffers(zero-copy)를 부분 도입하는 식으로 섞어 씁니다.

핵심 요약

  • 스키마 우선 + 바이너리 — 필드명을 안 보내고 번호로 식별해 작고 빠름.
  • oneof 봉투 패턴이 게임 실시간 메시지 라우팅의 사실상 표준.
  • 데이터 형태(PB)와 전송(TCP/UDP)은 분리 — 같은 메시지를 채널만 바꿔 사용.
  • 필드 번호는 불변 — reserved로 봉인, buf로 breaking 검사 → 라이브 무중단.
  • 압축·암호화가 아니므로 TLS·압축은 별도로 챙긴다.

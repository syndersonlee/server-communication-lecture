HTTP & HTTPS

가장 많이 쓰는 프로토콜. 버전 진화와 보안(TLS)까지 정확히 이해합니다.

⏱ 약 30분🎯 사용 케이스 · 도구 · 에러 대응 포함

📨 요청-응답 모델

클라이언트가 물어봐야 서버가 답한다. 서버가 먼저 못 보냄 → 실시간 기술의 출발점.

🧩 무상태 (Stateless)

각 요청은 독립적. 확장은 쉽지만 로그인 상태는 쿠키/세션/JWT로 따로 관리.

HTTP 버전의 진화 ⭐

각 버전은 이전 버전의 성능 한계를 극복하며 등장했습니다.

HTTP/1.1 1997

Keep-Alive로 연결 재사용. 하지만 HOL Blocking — 한 연결에서 응답은 보낸 순서대로 와야 해서, 앞 요청이 막히면 뒤가 전부 대기. 브라우저는 연결을 6개씩 열어 회피.

요청 A (느림)
⛔
응답 B 대기
응답 C 대기

B·C가 준비돼도 A가 끝날 때까지 막힘 (HOL Blocking)

HTTP/2 2015 · 성능 혁명

  • 멀티플렉싱: 하나의 TCP 연결에서 여러 요청/응답을 스트림으로 동시에 → HTTP HOL 해결
  • 바이너리 프레이밍 + 헤더 압축(HPACK)
⚠️

그래도 TCP 레벨 HOL 잔존 — 패킷 1개 유실이 모든 스트림을 막음.

HTTP/3 2022 · TCP를 버리다

  • QUIC(UDP 기반) 위에서 동작 → 스트림이 독립적이라 TCP HOL까지 해결
  • 연결 수립이 빠름(1-RTT/0-RTT), Wi-Fi↔LTE 전환에도 연결 유지

Spring 클라이언트

HTTP Clients
// ① RestClient (Spring 6.1+, 동기·모던) — 단순 호출 권장
RestClient client = RestClient.create("https://api.yanolja.com");
Reservation r = client.get().uri("/r/{id}", 9001)
        .retrieve().body(Reservation.class);

// ② WebClient (논블로킹) — 비동기/리액티브 필요 시 (6장)
Mono<Reservation> mono = webClient.get().uri("/r/9001")
        .retrieve().bodyToMono(Reservation.class);
💡

신규 코드는 RestClient(동기) / WebClient(논블로킹). RestTemplate는 유지보수 모드라 신규 사용 비권장.

HTTPS와 TLS

HTTPS = HTTP over TLS. 기밀성·무결성·인증을 보장합니다(포트 443).

🔐 인증서 & CA

CA의 서명으로 서버 신원을 보증. 브라우저/OS가 신뢰하는 Root CA 체인으로 검증.

🤝 mTLS

서버·클라 양방향 인증. MSA 내부, 제로 트러스트 보안에 사용.

⚠️

인증서 만료 장애는 정말 흔합니다. Let's Encrypt 등으로 자동 갱신 + 모니터링 필수. 실무에선 LB/게이트웨이에서 TLS 종료가 일반적.

에러 케이스 & 대응

실무에서 자주 만나는 증상 → 원인 → 대응.

🛟 에러별 대형 다이어그램으로 자세히 보기504·502·CORS·TLS·429·중복결제를 "문제 → 대응" 흐름으로 크게 분석 트러블슈팅 →
504 Gateway Timeout
원인

업스트림(앱) 응답이 LB/게이트웨이 타임아웃을 초과. 느린 쿼리·외부 호출 지연·스레드 풀 고갈.

대응

느린 구간 프로파일링 → 쿼리/인덱스 개선, 클라이언트 타임아웃을 게이트웨이보다 짧게 설정, 서킷브레이커로 빠른 실패, 필요한 작업은 비동기(5장)로 분리.

502 Bad Gateway
원인

업스트림이 죽었거나 비정상 응답. 배포 중 인스턴스 교체, OOM, 커넥션 강제 종료.

대응

헬스체크/그레이스풀 셧다운 설정, 롤링 배포 시 커넥션 드레이닝, keep-alive 타임아웃을 LB보다 길게 맞춰 idle 커넥션 재사용 충돌 방지.

CORS policy: No 'Access-Control-Allow-Origin'
원인

브라우저가 다른 출처(origin) 요청을 차단. 프리플라이트(OPTIONS) 미허용.

대응

서버에 @CrossOrigin 또는 글로벌 CorsConfiguration으로 허용 출처·메서드·헤더 명시. 운영에선 * 대신 도메인 화이트리스트.

SSLHandshakeException: PKIX path building failed
원인

JVM truststore에 상대 서버의 CA 인증서가 없음(사내 자체 서명 인증서 등).

대응

CA 인증서를 truststore에 추가(keytool -importcert), 인증서 체인 누락 점검, 도메인-인증서 CN/SAN 일치 확인.

429 Too Many Requests
원인

서버 측 레이트 리밋 초과(상대 API의 쿼터 포함).

대응

Retry-After 헤더 존중 + 지수 백오프 & 지터 재시도. 호출 측은 토큰버킷으로 자체 스로틀링.

중복 처리 (재시도로 인한 이중 결제)
원인

멱등하지 않은 POST를 네트워크 오류 후 재시도.

대응

Idempotency-Key 헤더로 서버가 중복 요청을 한 번만 처리하도록 보장.

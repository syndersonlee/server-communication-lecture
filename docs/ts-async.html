컨슈머 랙(Consumer Lag) 폭증

생산 속도 ≫ 소비 속도 → 처리 지연 누적

컨슈머가 생산을 못 따라가 메시지가 큐에 쌓이고, 실시간성이 무너집니다.

예방 — 컨슈머 처리 시간을 짧고 일정하게 유지하도록 설계.

독성 메시지(Poison Message) 무한 재시도

처리할 수 없는 한 건이 오프셋 진행을 막아 뒤따르는 모든 메시지를 멈춥니다.

  3. 스키마 검증으로 사전 차단

🟠 Warning

🔴 Critical

DB 커밋과 메시지 발행 불일치

DB는 저장됐는데 메시지는 유실 (또는 반대)

DB 트랜잭션과 브로커 발행은 서로 다른 시스템이라 원자적이지 않습니다. 둘 사이에 장애가 나면 정합성이 깨집니다.

Transactional Outbox
BEFORE · 문제
💾DB commit
→그 직후 크래시
📮발행 못함
✗
🕳️이벤트 유실

💥 저장과 발행 사이 장애 → 불일치

AFTER · 대응
💾DB + outbox같은 트랜잭션
→
📤릴레이/CDC
→재시도 보장
✅브로커 발행

✅ 이벤트를 같은 트랜잭션에 outbox로 저장 후 별도 발행

🔍증상
  • 주문은 있는데 알림/후속 이벤트 없음
  • 또는 이벤트만 있고 데이터 없음
⚠️원인
  • DB·브로커 이중 쓰기(dual write)
🩺진단
  • 데이터-이벤트 정합성 대사(reconcile)
✅대응
  1. Transactional Outbox 패턴 도입
  2. 릴레이/CDC(Debezium)로 발행
  3. 컨슈머는 멱등 처리
🛡️
예방 — "DB와 브로커 동시 쓰기 금지"를 원칙으로, outbox를 표준화.

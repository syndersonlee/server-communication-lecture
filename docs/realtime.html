Long Polling

새 이벤트 생길 때까지 응답 보류

  • 실시간성 ↑, 빈 응답 ↓
  • 연결 보류 관리 필요
  • 여전히 매번 새 요청
PollingController.java
// Long Polling — DeferredResult로 스레드 점유 없이 보류
@GetMapping("/long-poll")
public DeferredResult<List<Event>> longPoll() {
    DeferredResult<List<Event>> d = new DeferredResult<>(30_000L, List.of());
    waiting.add(d);
    return d;  // ★ 톰캣 워커 스레드는 즉시 반납
}
💡

DeferredResult의 핵심: 응답을 보류해도 서블릿 스레드를 점유하지 않습니다.

② SSE (Server-Sent Events)

하나의 HTTP 연결로 서버 → 클라이언트 단방향 스트리밍. 알림·피드·시세·LLM 토큰 스트리밍에 최적.

Client
◀── event ──
◀── event ──
◀── event ──
Server

한 번 열린 연결로 서버가 계속 push (클라는 받기만)

🔁 자동 재연결

EventSource가 끊기면 자동 재접속, Last-Event-ID로 이어받기

📄 HTTP 그대로

프로토콜 업그레이드 불필요, text/event-stream

➡️ 단방향

서버→클라만. 텍스트 전용

SseController.java
@GetMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter subscribe() {
    SseEmitter emitter = new SseEmitter(60_000L);
    emitters.add(emitter);
    return emitter;   // 이후 emitter.send(...)로 단방향 push
}
💡

ChatGPT 같은 LLM 응답 스트리밍도 대부분 SSE입니다. 단방향이면 WebSocket보다 SSE가 거의 항상 정답.

③ WebSocket

하나의 연결로 양방향(full-duplex) 실시간 통신. 채팅·게임·협업에 최적.

Client
◀══▶ws / wss
Server

서버도 보내고 클라도 보내고 — 연결 유지, 가벼운 프레임 단위

핸드셰이크: 101 Switching Protocols

HTTP 요청으로 시작 → Upgrade: websocket → 서버가 101로 응답하면 그 TCP 연결이 WebSocket으로 전환됩니다. (80/443 포트라 방화벽 친화적)

STOMP — pub/sub
@MessageMapping("/chat.send")   // 클라가 /app/chat.send 로 전송
@SendTo("/topic/room")          // /topic/room 구독자 전체에게 브로드캐스트
public ChatMessage send(ChatMessage msg) { return withTime(msg); }
⚠️

다중 서버 확장 시 내장 SimpleBroker로는 부족 → RabbitMQ/Redis 등 외부 브로커 relay 필요. 수만 동시 연결은 비동기(Netty) 모델이 유리(6장).

🔁 Short Polling — 실제 사용

"가끔, 단순하게, 결과만 확인하면 될 때." 인프라 변경 없이 가장 빨리 붙일 수 있어 비동기 작업의 상태 확인에 광범위하게 쓰입니다.

💳 결제 상태 확인

결제창(리다이렉트/팝업) 이후 "결제 완료됐나?"를 수 초 간격으로 조회. PG/카드사 콜백 지연을 흡수.

⚙️ 비동기 잡(Job) 결과

영상 인코딩·대용량 리포트/엑셀 생성·AI 이미지 생성처럼 오래 걸리는 작업을 jobId로 받아 GET /jobs/{id} 폴링.

🏗️ CI/CD · 배포 상태

빌드/배포 파이프라인 진행 상태를 주기 조회(예: GitHub Actions 상태 확인 UI).

📱 모바일 백그라운드 동기화

메일 새로고침, 주기적 데이터 동기화 등 저빈도 갱신.

🧭

왜 Short Polling인가 — 구현이 가장 단순(일반 GET), 서버 상태를 안 들고 있어도 됨, 방화벽·프록시 무난, 갱신 주기가 수 초~수십 초로 느슨하면 충분. 실시간성이 필요해지는 순간 SSE/WS로 갈아타야 합니다.

⏳ Long Polling — 실제 사용

"준실시간이 필요한데 SSE/WebSocket을 못 쓸 때"의 현실적 타협안. 과거 웹 채팅·알림의 표준이었고 지금도 폴백 경로로 살아 있습니다.

💬 초기 웹 메신저

WebSocket 보급 이전의 Facebook Chat·Gmail Chat 등 웹 채팅 알림이 long polling 기반이었음.

🏢 엄격한 기업 환경

WS 업그레이드를 막는 사내 프록시/구형 브라우저에서 준실시간 알림을 받아야 할 때.

🔌 폴백 트랜스포트

Socket.IO·SockJS가 WS 불가 시 자동으로 long polling으로 폴백하는 안전망.

📨 이벤트 대기형 API

"새 메시지 올 때까지 기다렸다 응답"하는 메시지 큐 소비형 엔드포인트.

🧭

왜 Long Polling인가 — HTTP만으로 빈 응답 없이 준실시간을 흉내. 다만 매번 새 요청이라 오버헤드가 있고 보류 연결 관리가 필요 → 가능하면 SSE/WS가 우선, Long Polling은 호환성 폴백으로 두는 것이 정석.

📡 SSE — 실제 사용

"서버가 일방적으로 계속 흘려보내는" 거의 모든 화면. 기존 HTTP 인프라를 그대로 쓰면서 자동 재연결까지 공짜라, 읽기 전용 실시간의 사실상 표준입니다.

ChatGPT·Claude·Gemini·Perplexity 등 토큰이 생성되는 대로 흘려보내는 스트리밍의 표준.

💡

왜 SSE인가 — 방향이 서버→클라 단방향이면 WebSocket의 양방향 복잡도가 불필요. 게다가 ① 그냥 HTTP라 LB·프록시·인증·HTTP/2를 그대로 사용, ② EventSource가 끊김을 자동 재연결 + Last-Event-ID로 누락 복구, ③ 구현이 단순. 대용량 동시 스트림이면 WebFlux로 백프레셔를 더하면 됩니다.

🔌 WebSocket — 실제 사용

"양쪽이 수시로, 낮은 지연으로 주고받아야 할 때." 채팅부터 협업·게임·트레이딩까지 인터랙티브 실시간의 핵심.

Slack·Discord·라인/카카오 웹, 고객센터 실시간 상담. 입력/수신이 동시에 빈번.

방송 중 실시간 댓글·하트·구매 알림 등 고빈도 양방향 상호작용.

실시간 위치 · 경매

배달 라이더 위치 추적, 실시간 입찰/경매처럼 즉시성이 중요한 양방향.

WebSocket
💡

왜 WebSocket인가 — 한 번 연결하면 양방향으로 가벼운 프레임을 계속 주고받아 요청마다 헤더를 새로 붙이는 비용이 없고 지연이 낮음. 채팅·협업은 STOMP pub/sub으로 방(room) 모델을 얹고, 다중 서버로 키우면 외부 브로커 relay가 필요합니다. 초저지연·P2P가 필요하면 WebRTC를 함께 검토하세요.

🧭

한 줄 정리 — 결과만 가끔 확인 → Short Polling, 준실시간인데 WS 불가 → Long Polling, 서버가 일방적으로 흘려보냄 → SSE, 양쪽이 수시로 주고받음 → WebSocket.

에러 케이스 & 대응

🛟 에러별 대형 다이어그램으로 자세히 보기SSE 버퍼링·연결 끊김·WS 핸드셰이크·다중서버·연결 폭증을 크게 분석 트러블슈팅 →
SSE 이벤트가 한참 뒤 몰아서 도착
원인

프록시(Nginx 등)가 응답을 버퍼링. 실시간성이 깨짐.

대응

proxy_buffering off + 응답 헤더 X-Accel-Buffering: no. 주기적 heartbeat(:ping)로 연결 유지.

SSE 연결이 일정 시간마다 끊김
원인

LB/서버 idle timeout, HTTP/1.1 브라우저 연결 수 제한(도메인당 6개) 초과.

대응

EventSource 자동 재연결 + Last-Event-ID로 이어받기 구현, 타임아웃 상향, HTTP/2 적용으로 연결 수 제한 회피.

WebSocket: Error during handshake (200/403)
원인

프록시가 Upgrade 헤더를 전달 안 함, 또는 CORS/Origin 거부.

대응

프록시에 proxy_set_header Upgrade $http_upgrade; Connection "upgrade"; 추가, 서버 setAllowedOriginPatterns 설정.

메시지가 일부 사용자에게만 안 감 (다중 서버)
원인

A서버 구독자에게 B서버에서 발생한 이벤트가 전달 안 됨(내장 SimpleBroker는 인스턴스 로컬).

대응

Redis Pub/Sub 또는 외부 STOMP 브로커 relay로 서버 간 메시지 공유. 세션 정보 공유 설계.

연결 수 폭증 → 스레드/메모리 고갈
원인

BIO(연결당 스레드) 모델로 수만 동시 연결 처리.

대응

비동기(Netty/WebFlux) 모델로 적은 스레드로 많은 연결 처리(6장). 죽은 연결은 ping/pong heartbeat로 정리.

SSE에서 emitter.send() 시 IOException
원인

클라이언트가 이미 연결을 끊었는데 서버가 전송 시도.

대응

try/catch로 잡아 해당 emitter를 컬렉션에서 제거. onCompletion/onTimeout/onError 콜백에서 정리.

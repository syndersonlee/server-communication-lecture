CHAPTER 4

gRPC & GraphQL

REST를 넘어서 — 서버 간 고성능 통신(gRPC)과 유연한 데이터 조회(GraphQL).

⏱ 약 40분 (2개 기법)🎯 사용 케이스 · 도구 · 에러 대응

gRPC

구글이 만든 고성능 RPC. 원격 함수를 로컬 함수처럼 호출합니다. 주로 MSA 내부 서버 간 통신에 사용.

⚙️ HTTP/2

멀티플렉싱·스트리밍·헤더압축 기본

📦 Protobuf

바이너리 직렬화 → JSON보다 작고 빠름

📜 IDL(.proto)

계약 우선 정의 → 다국어 코드 자동 생성

user.proto + Spring
// 계약 정의
service UserService {
  rpc GetUser (GetUserRequest) returns (UserResponse);
}

// 서버
@GrpcService
public class UserServiceImpl extends UserServiceImplBase {
    @Override public void getUser(GetUserRequest req, StreamObserver<UserResponse> obs) {
        obs.onNext(...); obs.onCompleted();
    }
}

4가지 통신 방식

Unary(단일) · Server Streaming · Client Streaming · Bidirectional(양방향) — HTTP/2 스트리밍 덕분.

⚠️

브라우저는 HTTP/2 프레임을 raw로 못 다뤄 직접 호출 불가(gRPC-Web + 프록시 필요). 그래서 외부 공개는 REST, 내부는 gRPC가 전형적입니다.

GraphQL

클라이언트가 필요한 데이터의 형태를 직접 명시해서 요청. 단일 엔드포인트(/graphql)에 POST.

😵 REST의 문제

  • Over-fetching: 이름만 필요한데 전부 받음
  • Under-fetching: 화면 하나에 N번 호출
→

😎 GraphQL

  • 필요한 필드만, 한 번의 요청으로
  • 강타입 스키마, 자동 문서화
query
query {
  user(id: 1) {
    name
    reservations { checkIn  hotel { name } }   // 필요한 것만
  }
}
⚠️

대가: HTTP 캐싱 곤란(POST 단일 엔드포인트), N+1 문제(→ DataLoader 배치 로딩), 쿼리 복잡도 제어 필요. 다양한 클라이언트가 다른 데이터를 요구하는 BFF에 강점.

세팅 & 도구

gRPC

protoc / bufCLI

GraphQL

스키마 탐색·쿼리 자동완성. Spring은 /graphiql 기본 제공.

에러 케이스 & 대응

gRPC

UNAVAILABLE: io exception / Connection refused
원인

서버 미기동, 네트워크 단절, 서버 재시작 중. 가장 흔한 gRPC 에러.

대응

클라이언트 재시도(지수 백오프) + deadline 설정, keepalive 설정, 로드밸런싱(클라이언트 사이드 LB/네임 리졸버).

DEADLINE_EXCEEDED
원인

호출이 설정한 deadline을 초과. 다운스트림 지연 누적.

대응

호출마다 적절한 deadline 전파(deadline propagation), 느린 RPC 분리, 스트리밍으로 부분 응답.

RESOURCE_EXHAUSTED: message exceeds max size
원인

기본 메시지 크기(4MB) 초과.

대응

maxInboundMessageSize 상향 또는 스트리밍으로 분할 전송. 대용량은 객체 스토리지 URL 전달 고려.

브라우저에서 gRPC 직접 호출 실패
원인

브라우저가 HTTP/2 프레임을 raw로 제어 불가.

대응

gRPC-Web + Envoy 프록시 사용, 또는 외부는 REST/GraphQL로 노출하고 내부만 gRPC.

GraphQL

응답은 느린데 DB 쿼리가 수백 개 (N+1)
원인

필드 리졸버가 항목마다 개별 쿼리 실행.

대응

DataLoader로 배치 로딩 + 캐싱. 쿼리 단위 캐시 적용.

깊은 중첩 쿼리로 서버 과부하
원인

악의적/실수로 매우 깊거나 넓은 쿼리 요청.

대응

쿼리 depth/complexity 제한, persisted query(허용된 쿼리만), 타임아웃·페이지네이션 강제.

HTTP 200인데 errors 배열에 에러
원인

GraphQL은 부분 실패를 200 + errors로 표현(상태코드로 판단 불가).

대응

클라이언트가 errors를 반드시 검사, 서버는 일관된 에러 포맷·코드 체계 정의.

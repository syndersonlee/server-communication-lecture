CHAPTER 5

비동기 메시징

"메시지를 던져놓고 내 할 일 하기." 동기 호출의 강결합과 장애 전파를 끊습니다.

왜 비동기인가

😰 동기 (직접 호출)

주문→ 결제→ 재고
  • 하나만 죽어도 전체 실패
  • 응답시간 = 모든 단계 합
  • 강결합
VS

😎 비동기 (메시지)

주문→ 브로커⇉ N개 소비
  • 던지고 즉시 응답
  • 장애 격리·트래픽 완충
  • 느슨한 결합

📮 메시지 큐 (P2P)

하나의 메시지를 한 컨슈머가 가져감 → 작업 분배

📡 Pub/Sub

하나의 메시지를 구독자 모두가 받음 → 브로드캐스트

RabbitMQ vs Kafka

RabbitMQKafka
모델메시지 브로커(큐)이벤트 로그/스트림
소비 후삭제보존(재처리 가능)
처리량중간매우 높음
강점복잡한 라우팅, 작업 큐대용량 이벤트, EDA 중추
Kafka — Spring
// 발행
kafkaTemplate.send("orders", String.valueOf(event.orderId()), event);

// 소비
@KafkaListener(topics = "orders", groupId = "inventory-service")
public void consume(OrderCreatedEvent event) {
    inventoryService.decrease(event.getProductId(), event.getQty());
}

MQTT는 초경량 pub/sub 프로토콜로 IoT·모바일 등 저전력 환경에 최적입니다(QoS 0/1/2).

비동기의 대가 ⚠️

비동기는 공짜가 아닙니다. 반드시 설계해야 할 것들:

🔁 메시지 중복

대개 at-least-once → 멱등 컨슈머 필수

🔢 순서 보장

전역 순서 어려움 → Kafka 파티션 키로 부분 보장

💀 실패 처리

실패 메시지를 DLQ로 보내 재처리/분석

🔗 정합성

DB 저장+발행을 함께 → Transactional Outbox

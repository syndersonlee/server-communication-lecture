비동기 메시징

"메시지를 던져놓고 내 할 일 하기." 동기 호출의 강결합과 장애 전파를 끊습니다.

⏱ 약 30분🎯 사용 케이스 · 도구 · 에러 대응

왜 비동기인가

😰 동기 (직접 호출)

주문→ 결제→ 재고
  • 하나만 죽어도 전체 실패
  • 응답시간 = 모든 단계 합
  • 강결합
VS

😎 비동기 (메시지)

주문→ 브로커⇉ N개 소비
  • 던지고 즉시 응답
  • 장애 격리·트래픽 완충
  • 느슨한 결합

📮 메시지 큐 (P2P)

하나의 메시지를 한 컨슈머가 가져감 → 작업 분배

📡 Pub/Sub

하나의 메시지를 구독자 모두가 받음 → 브로드캐스트

비동기의 대가 ⚠️

비동기는 공짜가 아닙니다. 반드시 설계해야 할 것들:

🔁 메시지 중복

대개 at-least-once → 멱등 컨슈머 필수

🔢 순서 보장

전역 순서 어려움 → Kafka 파티션 키로 부분 보장

💀 실패 처리

실패 메시지를 DLQ로 보내 재처리/분석

🔗 정합성

DB 저장+발행을 함께 → Transactional Outbox

에러 케이스 & 대응

Consumer Lag 폭증 (소비가 생산을 못 따라감)
원인

컨슈머 처리 속도 < 생산 속도. 무거운 처리, 파티션 부족.

대응

파티션 수 ↑ + 컨슈머 인스턴스 ↑(병렬성), 처리 로직 경량화/배치, 무거운 작업은 비동기 분리. lag 알람 설정.

메시지 중복 처리 (이중 결제/이중 적립)
원인

at-least-once 전달 + 컨슈머 재시작/리밸런싱 시 재처리.

대응

멱등 컨슈머: 처리한 메시지 ID를 저장해 중복 스킵, 또는 upsert/조건부 업데이트로 멱등하게 설계.

CommitFailedException / 리밸런싱 반복
원인

max.poll.interval.ms 안에 처리 못 끝내 그룹에서 추방 → 리밸런싱 폭풍.

대응

한 번에 가져오는 레코드 수(max.poll.records) 축소, 처리 시간 단축, 인터벌 상향, 무거운 작업은 별도 스레드.

처리 실패 메시지가 무한 재시도 (poison message)
원인

특정 메시지가 계속 예외 → 컨슈머가 그 자리에서 멈춤.

대응

재시도 횟수 제한 후 DLQ(Dead Letter Queue)로 보내 격리·분석. 재처리 파이프라인 구성.

순서가 뒤바뀐 채 처리됨
원인

여러 파티션/컨슈머로 분산되어 전역 순서 미보장.

대응

순서가 중요한 키(예: 주문ID)를 파티션 키로 지정 → 같은 키는 같은 파티션 → 순서 보장.

DB는 커밋됐는데 메시지가 발행 안 됨 (정합성 깨짐)
원인

DB 트랜잭션과 메시지 발행이 분리되어 한쪽만 성공.

대응

Transactional Outbox: 같은 DB 트랜잭션에 outbox 테이블 기록 → 별도 릴레이가 발행. (또는 CDC/Debezium)
